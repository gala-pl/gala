---
title: GIR
description: Gala’s typed intermediate representation and its role as the backend contract.
---

GIR is defined in `crates/gala-gir`. It models functions, basic blocks, nodes, values, types,
constants, and terminators in a serializable Rust data model.

## Main concepts

- `Gir` owns the function collection.
- `GirFunc` owns blocks, arguments, return type, and effect metadata.
- `Block` owns ordered operation nodes and a terminator.
- `GirNode` carries a `NodeKind` plus inputs and outputs.
- `NodeKind` distinguishes quantum gates, allocation, measurement, classical operations, calls,
  and constants.
- `GirType` and `TypeKind` represent classical, quantum, tuple, array, and measured shapes.

The representation uses stable numeric IDs for functions, blocks, nodes, values, types, and
constants. This makes dumps and later JSON schemas possible without coupling backend code to HIR
internals.

## Lowering

`lower_hir_to_gir` receives HIR functions together with type and effect maps. It translates the
checked semantic representation into GIR and can report diagnostics for unsupported lowering
cases.

## What GIR does not promise yet

GIR is the architectural seam, not proof that every backend is complete. Optimization, gradient
lowering, simulation, classical codegen, and QIR emission currently expose APIs with partial or
placeholder behavior. Backend work should add golden GIR/QIR tests and execution tests before
claiming a new path is production-ready.
