Gala is designed to target several execution modes from one GIR:

| Component | Intended role | Current repository state |
| --- | --- | --- |
| `gala-sim` | state-vector, noisy, and tensor-network execution | configuration/result types exist; runners return placeholder errors |
| `gala-runtime` | backend registration, capability checks, dispatch, batching | data model and traits exist; execution is not wired through |
| `gala-qir` | emit LLVM-based QIR | emits a minimal module shell, not gate-level QIR |
| `gala-codegen-classical` | native classical orchestration | target enum exists; emission returns an error placeholder |

## Backend capabilities

The runtime capability model includes a backend name, qubit count, native gates, connectivity,
mid-circuit measurement support, and reset support. That information is intended to drive target
lowering and capability diagnostics.

## Simulation design

`SimConfig` selects `StateVector`, `Noisy`, or `TensorNetwork`, with shots, an optional seed, and
an optional noise model. `SimResult` reserves counts, probabilities, state-vector data, and shot
metadata. The execution algorithms are not implemented yet, so these types are planning and API
scaffolding rather than a runnable simulator.

## QIR design

`QirProfile` has `Base` and `Adaptive` variants. The intended future behavior is to choose adaptive
QIR when mid-circuit measurement or measurement-conditioned control flow is present. The current
emitter writes a module header, target triple, and empty function bodies; it does not yet encode
GIR operations or validate profile capabilities.

## Extension path

A complete backend should consume GIR, declare capabilities, execute or emit an artifact, surface
structured diagnostics, and add conformance coverage. It should not reimplement lexing, type
checking, or linear ownership.
