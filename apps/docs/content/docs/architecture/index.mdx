title: Architecture
description: How the Rust workspace separates syntax, semantics, GIR, and execution.

Gala is a Cargo workspace. The intended architecture has a strict boundary: frontend crates turn
source into typed GIR, and backend crates consume GIR without importing the frontend.

## Workspace map

```text
source (.gala)
  │
  ├─ gala-lexer       tokens and spans
  ├─ gala-parser      AST with recovery
  ├─ gala-ast         syntax data types
  ├─ gala-hir         desugaring, definitions, module graph
  ├─ gala-types       types, effects, linearity
  ├─ gala-uncompute   provenance and release plans
  └─ gala-gir         typed intermediate representation
          │
          ├─ gala-diff             gradient lowering
          ├─ gala-opt              GIR rewrites
          ├─ gala-qir              QIR emission
          ├─ gala-sim              simulation
          ├─ gala-runtime          backend dispatch
          └─ gala-codegen-classical native classical codegen
```

Supporting crates provide source spans, diagnostics, the CLI, formatting, package manifests,
standard-library helpers, linting, and the language-server entry point.

## Important boundaries

- **AST versus HIR:** AST mirrors source syntax; HIR is the semantic, desugared form.
- **Checks before GIR:** type, effect, linearity, and uncomputation diagnostics are emitted before
  lowering a successful function to GIR.
- **GIR as a contract:** backends should consume typed operations rather than reimplementing
  frontend rules.
- **Runtime versus codegen:** codegen produces artifacts; runtime dispatches programs to a backend.

## Current implementation

The workspace contains the crate boundaries and many usable data models, but several downstream
passes are intentionally minimal. Read [the pipeline](/docs/architecture/pipeline) and
[implementation status](/docs/reference/status) together: the design is broader than the current
executable behavior.
